# Linear-probe preflight — Qwen3.5-9B activations for the v2 exchange classifier

**Read-only preflight. No probe was trained, no activations were extracted, no model was
loaded on GPU, no forward pass was run, and no existing file was modified.** Everything below
was derived by reading code, config files, and metadata, and by running the local tokenizer
(CPU only) — never the model.

---

## Answers to the 10 required questions (read this first)

**1. Šta tačno već postoji?**
A 288-row (285 physically usable) corpus of Qwen3.5-9B residual-stream activations across two
buckets — `local_replay/` (38 jailbreak replays, all harmful) and `plain_prompts/` (250 plain
prompts, 125 harmful-refusal + 125 benign) — captured while Qwen **generated its own response**
to each prompt, at 8 full-attention layers, fp16, span = last 64 prompt tokens + full response.
No probe-training code exists anywhere in the repo (confirmed by exhaustive search).

**2. Koliko imamo stvarnih, upotrebljivih activation primera?**
**285**, not 288. 3 metadata rows (`template_id=grok-420` for `trans-75002-pl`,
`trans-9727-pt`, `orig-30940`) point at a `.npz` file that was silently overwritten by a later
`hermes-fast` run for the same `row_id` — definitively proven (not merely suspected) via
token-count and exact decoded-text matching (section 3).

**3. Da li postoje leakage i duplikati?**
No cross-split leakage — 0 `original_idx` groups span more than one v2 split (v2 splits are
group-disjoint by construction, confirmed here directly). But **28 `original_idx` groups (of
253) have 2-3 activation rows each within the same split**, including 8 groups whose rows come
from *both* buckets (the same prompt appears once self-generated-plain and once
jailbreak-wrapped). A naive row-level split for the probe's *own* train/val partition would
leak near-duplicate content (section 4).

**4. Da li postojeće aktivacije predstavljaju isti input kao v2 klasifikatori?**
**No, not the response half.** The prompt text is byte-identical to v2's `prompt` field in
100% of rows (288/288). But the response is **always freshly generated by Qwen itself** —
0/288 rows have a response matching v2's stored `response` field, and 0/288 represent the
exact same `(prompt, response)` exchange a v2 classifier would see. These are
**self-generation activations, not teacher-forced v2-exchange activations** (section 5).

**5. Da li ih možemo koristiti kao glavni probe-training dataset?**
Not without a decision first (see `open_questions.md` #1). As-is they train a probe for a
*different* task ("is Qwen's own completion of this prompt harmful") than "reproduce the v2
exchange label," even though the binary target happens to coincide for prompt-driven rows.

**6. Da li ih možemo koristiti kao pomoćni/pilot/robustness dataset?**
Yes, and this looks like the safer near-term role: 285 real Qwen3.5 forward passes, already
captured, zero extraction cost, useful for a first pipeline test (pooling code, standardization,
train/val split logic, sanity-check layer sweep) before committing to a full v2 extraction.

**7. Da li treba izvući nove kompaktne v2 aktivacije?**
If the goal is a probe whose training distribution matches what Gemma/Qwen3Guard were actually
evaluated on (the v2 `(prompt, response)` pairs) — **yes**. This preflight specifies the exact
format (section 7) and sizes it (section 9: ~160 MB for a pooled representation of all 2471
rows, or ~84 GB for full token-level) but does not extract anything.

**8. Koji exact input-format je metodološki najispravniji?**
Reuse the native Qwen chat template with `enable_thinking=False`, tokenize the prompt-plus-empty-think-block
prefix and the response separately and concatenate (matching the existing scripts'
own method, verified byte-identical to the alternative "single `apply_chat_template` call"
method except for one optional trailing newline). Full spec in section 7. The empty-response
case has two defensible boundary choices, not yet decided (`open_questions.md` #2).

**9. Koje pooling opcije postoje?**
Four sized in section 9: full token-level (84 GB/2471 rows), last-token (162 MB), mean-pooled
(162 MB), and prompt-mean+response-mean+last-token (486 MB). No pooling code exists yet
(section 10).

**10. Koje odluke još moramo doneti pre implementacije?**
Eight, enumerated in full in `open_questions.md` — most importantly: (a) self-generation vs.
teacher-forced as the primary training distribution, (b) the empty-response format boundary,
(c) whether to special-case the post-norm layer 31, (d) what to do with the 3 stale rows, (e)
group-aware split for the probe's own train/val.

## 2. Qwen3.5-9B architecture and tokenizer (from local config only, no weights loaded)

Full detail in `model_tokenizer_summary.json`. Headline facts, all read directly from
`/data/models/Qwen3.5-9B/config.json`, `tokenizer_config.json`, `chat_template.jinja`, and the
actual installed `transformers==5.15.0` source in `qwen35_env` — none assumed from comments:

- **Architecture**: `Qwen3_5ForConditionalGeneration`, `model_type=qwen3_5`. A composite
  vision+text config (`image_token_id`/`video_token_id`/`vision_config` present) — irrelevant
  here, we only use `text_config`.
- **32 hidden layers, hidden_size=4096, 16 attention heads (head_dim=256), 4 KV heads (GQA),
  vocab_size=248,320, max_position_embeddings=262,144**.
- **Hybrid architecture, NOT a plain transformer**: `full_attention_interval=4` — every 4th
  layer (0-indexed 3, 7, 11, ..., 31) is `full_attention`; the other 24 are `linear_attention`
  (a gated recurrent/conv-based linear-attention mechanism — `attn_output_gate=true`,
  `linear_conv_kernel_dim=4`, separate linear-attention head-dim/head-count fields — similar in
  spirit to Gated DeltaNet / Jamba-style hybrids).
- **CAPTURE_LAYERS=[3,7,11,15,19,23,27,31] used by both existing scripts are confirmed, by
  directly reading `config.json`'s `layer_types` list, to be exactly the 8 full-attention
  layers** — not an assumption from the code comment, an independent verification.
- **`hidden_states[l+1]` = output of decoder layer `l`** (0-indexed), confirmed both from the
  code comment and from the transformers-internal mechanism: `Qwen3_5Model` declares
  `_can_record_outputs = {"hidden_states": Qwen3_5DecoderLayer}`, so a hook fires once per
  decoder-layer forward call when `output_hidden_states=True`.
- **Layer 31 (the last captured layer) is POST-final-RMSNorm, not the raw pre-norm decoder
  output** — resolved definitively, not left open. `Qwen3_5Model.forward` is decorated
  `@capture_outputs` (bare, default `tie_last_hidden_states=True`) from
  `transformers/utils/output_capturing.py`. That decorator's documented behavior — verified by
  reading its source — is to **overwrite `hidden_states[-1]` with `last_hidden_state`**
  whenever the model output has a `last_hidden_state` attribute (it does). `Qwen3_5Model.forward`
  computes `last_hidden_state = self.norm(hidden_states)` (line 1209) — i.e. after the model's
  one final `Qwen3_5RMSNorm`. **Consequence: 7 of the 8 captured layers (3,7,11,15,19,23,27)
  are raw residual-stream values; the 8th (31) has been renormalized and is on a different
  scale.** Worth accounting for before pooling/standardizing across layers (see
  `open_questions.md` #3).
- **Tokenizer**: `eos_token="<|im_end|>"` (id 248046), `pad_token="<|endoftext|>"` (id 248044),
  no `bos_token`, `<|im_start|>` id 248045. **No `generation_config.json` ships with the
  checkpoint** (confirmed: file does not exist) — matches the already-documented CLAUDE.md
  pitfall about `generate()` not stopping at `<|im_end|>` without explicitly passing both eos
  ids. Irrelevant for teacher-forced extraction (no `generate()` call needed).
- **Chat template** (`chat_template.jinja`): user turn = `<|im_start|>user\n{content}<|im_end|>\n`.
  With `add_generation_prompt=True, enable_thinking=False`: `<|im_start|>assistant\n<think>\n\n</think>\n\n`
  — an **empty** think block is inserted into the *prompt* itself (the model is never asked to
  emit its own `<think>` tags). An assistant message already present in the `messages` list
  (i.e. teacher-forcing) is rendered `<|im_start|>assistant\n<think>\n{reasoning_content}\n</think>\n\n{content}<|im_end|>\n`
  — and this branch does **not** consult `enable_thinking` at all; it wraps in an (empty, for
  our data) think block regardless. Verified empirically (tokenizer only) that this produces
  content-token-identical output to the generation-prompt-with-`enable_thinking=False` path
  (differs only by one optional trailing newline) — so the two candidate construction methods
  for Format A (below) are safely interchangeable.

## 3. Audit of existing activation files

Never loaded a full `hidden` array into RAM — only `token_ids` (tiny int32 arrays) were read
for verification.

| | metadata rows | unique `row_id` | physical `.npz` | disk |
|---|---:|---:|---:|---:|
| `local_replay/` | 38 | 35 | 35 | 3.93 GB |
| `plain_prompts/` | 250 | 250 | 250 | 10.82 GB |
| **combined** | **288** | **285** | **285** | **14.75 GB** |

Representative schema (both folders): `{"hidden": fp16 [8, n_tokens, 4096], "token_ids": int32 [n_tokens]}` — identical keys/dtypes in both buckets, only `n_tokens` varies per row.

**The 3 duplicate-`row_id` cases, resolved (not left ambiguous):** `trans-75002-pl`,
`trans-9727-pt`, `orig-30940` each have two metadata rows in `labeled_local.jsonl` (one per
template: `grok-420` and `hermes-fast`), because the source `successful_jailbreaks.jsonl` tested
both templates against the same prompt. `capture_activations()` writes to
`activations/{row_id}.npz` with **no template suffix**, so the second template processed for a
given `row_id` silently overwrites the first's file. Resolution method (tokenizer only, no
model): for each candidate metadata row, computed `expected_span_len = n_response_tokens +
min(prompt_tail, n_prompt_tokens)` and compared against the actual `.npz` `token_ids` length,
**and independently** decoded the `.npz`'s trailing `n_response_tokens` and compared against
each candidate's stored `response` string. Both checks agree, for all 3 row_ids: the surviving
`.npz` belongs to **`hermes-fast`**, not `grok-420` (exact length match + exact decoded-text
match for hermes-fast; both checks fail for grok-420). This is a hermes-fast-was-processed-second
artifact, not randomness — **not marked `ambiguous`, marked definitively wrong for the
grok-420 rows**. Recommendation: exclude those 3 `grok-420` metadata rows (already excluded
from every "usable" count in this report). Full per-row detail in `activation_manifest.csv`
and `npz_schema_audit.json`.

Metadata-vs-`.npz` token-count consistency (`n_response_tokens + min(64, n_prompt_tokens) ==
len(token_ids)`) holds for all 285 remaining rows — no other discrepancies found.

## 6. Label audit

**Formula**: `exchange_label = "harmful" if prompt_harm_label=="harmful" else ("harmful" if
response_harm_label=="harmful" else "safe")` for `local_replay` (prompt-only, since the prompt
is always harmful there); pure `prompt_harm_label` pass-through for `plain_prompts`. Vocabulary
differs from v2's (`{"harmful","safe"}` vs. v2's `{"harmful","unharmful"}`) but the underlying
rule is the same OR-of-prompt-and-response-harm rule documented in `PROBE_DATASET.md`. **Verified
here independently against `data/gemma_v2_no_refusal/{train,validation,test}.jsonl`
(not just the previously-documented `complete_dataset.jsonl` check): 0/288 real mismatches**
once the vocabulary difference is accounted for (a naive string-equality check falsely flags
all 125 `plain_prompts` "safe" rows as mismatches against v2's "unharmful" — same label,
different word).

- **Benign prompt + harmful response**: confirmed absent (0 rows) — matches
  `PROBE_DATASET.md`'s documented, accepted gap.
- **"Safe" rows verified as actually safe Qwen behavior**: only by construction (benign prompt
  ⇒ label safe), **not by inspecting the generated response** — no judge ever ran over
  `plain_prompts`' 125 "safe" responses. They are presumed safe, not verified safe.
- **Qwen3Guard response-label coverage**: `local_replay` 35/35 (100%, post-exclusion) have
  `guard_safety` (Safe 23 / Unsafe 8 / Controversial 4). `plain_prompts` **0/250** — all `guard_*`
  fields are `None` (no Qwen3Guard run was made, per the script's own docstring and confirmed
  in the data). **This is the concrete "what would need labeling" answer**: `plain_prompts/raw_plain.jsonl`,
  via the already-existing, unmodified `label_jailbreak_dataset.py` — only needed if pivoting to
  a response-only axis; not needed for the current exchange-label target.
- **Potential label noise**: the exchange target itself is prompt-driven and unambiguous for
  163/288 harmful rows (prompt is harmful by construction) — the noise risk is not in the
  label, it's in what a probe *learns to key off of* (next point).

**Confound / shortcut-signal audit** (aggregated statistics only):

- **Response length is a strong confound.** Mean `n_response_tokens`: `local_replay`
  (all-harmful, jailbreak-wrapped) 1648 tokens; `plain_prompts` harmful (refusals) 407 tokens;
  `plain_prompts` safe (helpful answers) 814 tokens. Within `plain_prompts` alone, safe
  responses are on average **2x longer** than harmful (refusal) responses — a probe using
  crude length-correlated features could partially "solve" the task without any real harm
  understanding.
- **`adversarial` is a near-perfect confound within `plain_prompts`**: `adversarial=True` → 100%
  safe (73/73, 0 harmful); `adversarial=False` → 125 harmful / 52 safe. Not itself a problem for
  the label (which never uses `adversarial`), but a real risk if a probe implicitly learns
  "does this look like a WildJailbreak-pool benign prompt" as a proxy feature.
- **`template_id` is 100% collinear with "harmful+jailbreak-wrapped" style** within
  `local_replay` (`grok-420` 23/35, `hermes-fast` 12/35, both only ever harmful) — a probe
  trained on the combined corpus could learn "looks like a G0DM0D3 divider template" as a
  shortcut for harmful, which would not generalize to non-jailbreak harmful content.
- **Language**: both classes in `plain_prompts` are near-identically stratified (2 rows/language
  for every non-English language in both classes, English scaled up ~30x per its pool share) —
  not a meaningful confound as constructed.
- **`finish_reason` (length-cap truncation)**: `plain_prompts` safe rows hit the 2048-token cap
  slightly more often (8/125) than harmful (2/125) — consistent with, not independent of, the
  response-length confound above.
- **Guard-label coverage asymmetry** (repeated from above): only 35/285 usable rows have any
  response-level judge signal at all; a probe that implicitly relies on response content quality
  signals correlated with guard labels would be trained on a very unevenly-labeled slice.

Full breakdowns computed and printed during this preflight (not re-saved as a separate CSV,
per the task's file list — available by re-running the same `row_id`-keyed joins used above).

## 7. Exact v2 input-format preflight (synthetic examples only, no dataset content shown)

Native Qwen chat template, `enable_thinking=False`, tokenizer only — verified empirically
below, not just described.

### Format A — row with a response (teacher-forced)

```
messages = [{"role": "user", "content": PROMPT}]
prompt_text = tokenizer.apply_chat_template(messages, tokenize=False,
                                             add_generation_prompt=True, enable_thinking=False)
# => "<|im_start|>user\n{PROMPT}<|im_end|>\n<|im_start|>assistant\n<think>\n\n</think>\n\n"
prompt_ids   = tokenizer(prompt_text, add_special_tokens=False)["input_ids"]
response_ids = tokenizer(RESPONSE, add_special_tokens=False)["input_ids"]
im_end_id    = tokenizer.convert_tokens_to_ids("<|im_end|>")
full_ids = prompt_ids + response_ids + [im_end_id]
```

Verified on a synthetic example (`"How do I bake a cake?"` / a 3-sentence synthetic answer):
19 prompt tokens + 17 response tokens + 1 eos = 37 total. The **last template token** before
any real content is the second `\n\n` closing the empty think block; the **first real content
token** is the first word of the response; the **last real content token** is the response's
final word/punctuation; the **last token overall** is the appended `<|im_end|>`.

**Verified equivalence to the alternative construction** (passing
`[{"role":"user",...}, {"role":"assistant","content":RESPONSE}]` through `apply_chat_template`
in one call): produces the same 37 tokens plus exactly one extra trailing `\n` — i.e. **no
retokenization-boundary distortion at the prompt/response junction**, the two methods are
interchangeable modulo that one newline. This preflight recommends the separate-tokenize-then-
concatenate method (matching the existing capture scripts) for consistency with the 285
existing activations, but both are equally valid (`open_questions.md` #2).

`add_generation_prompt=True` is used to get the same empty-think-block prefix the model would
see before generating — appropriate here even though we're not generating, because it's the
convention the existing 285 activations already use for their prompt/response boundary.

### Format B — row with `response == ""`

Two verified, both defensible, **not chosen**:

- **Option 1** (`add_generation_prompt=True`): identical to Format A's `prompt_ids` exactly
  (verified: same 19 tokens) — ends at the empty think block's closing `\n\n`, i.e. "the point
  right before Qwen would start generating." Consistent cut-point with Format A.
- **Option 2** (`add_generation_prompt=False`): `"<|im_start|>user\n{PROMPT}<|im_end|>\n"` — 12
  tokens for the same synthetic example — ends at the user turn's own `<|im_end|>`, i.e. "Qwen
  has just read the prompt, nothing more." Simpler, but a different boundary semantics than
  Format A.

No assistant section exists in Option 2; Option 1 has an assistant *header* (with an empty
think block) but no actual response content. Neither includes a trailing `<|im_end|>` after
content, since there is no content to close.

## 9. Compact-extraction space/compute estimate (no GPU run; estimates only)

Total tokens across all 2471 v2 rows (Format A/B as specified): **1,281,701** (avg 518.7/row).
Per-layer-set constant: 8 layers × 4096 dims × fp16 = 64 KB/token or 64 KB per pooled
`[8,4096]` vector.

| Option | Disk (2471 rows) | RAM to fully load | Notes |
|---|---:|---:|---|
| 1. Full token-level, 8 layers | **~84.0 GB** | ~84 GB (or streamed) | Only option preserving future token-level (mid-stream-stopping) probe training without re-extraction |
| 2. Last-token vector, 8 layers | **~162 MB** | ~162 MB | Cheapest; loses all within-exchange positional information |
| 3. Mean-pooled vector, 8 layers | **~162 MB** | ~162 MB | Same size as (2); smooths over the whole exchange, may dilute a short harmful tail in a long benign-looking prompt |
| 4. Prompt-mean + response-mean + last-token, 8 layers | **~486 MB** | ~486 MB | 3x size of (2)/(3); keeps the prompt/response distinction PROBE_DATASET.md's own recipe #1 (exchange-level probe) implicitly wants |

Disk: `/home/mls01` has 12 TB free, `/data` has 21 TB free — none of these four options is a
real disk constraint, including the 84 GB option. RAM: 927 GB currently available — trivially
enough to fully load any of the four in-process, no streaming required for training (though
streaming one row at a time would still be the simpler implementation for option 1, avoiding a
single 84 GB in-memory array).

**Runtime** (estimate only, derived from the existing `REPORT.md`s' own numbers, not
benchmarked here): both existing capture scripts report "~1-2 s/row" for a single
teacher-forcing pass (no autoregressive generation needed for extraction, only for the
self-generation captures that already exist). At that rate, 2471 rows ≈ **40-80 minutes**
total for a full v2 extraction pass, any pooling option (pooling is free relative to the
forward pass itself — computed from the same `hidden_states` output).

**Recommendation-flagged-as-non-binding**: given the runtime is cheap either way, extracting
option 4 (pooled) now and keeping the option open to re-extract option 1 (full token-level)
later — rather than committing to full token-level immediately — looks like the lower-regret
path, but this is exactly the kind of call this preflight was scoped to surface, not make
(`open_questions.md` #7).

## 10. Reusable code

Full detail in `reusable_code_inventory.md`. Headline: `capture_activations()` in both
`replay_jailbreaks_local.py` and `capture_plain_activations.py` is directly reusable for a new
teacher-forced extractor (it just slices `hidden_states` at `CAPTURE_LAYERS` and saves — doesn't
care where `full_ids` came from); everything generation-related (`model.generate()`, eos/pad
